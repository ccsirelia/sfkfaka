# LIMEN 礼门 · 卡密兑换中心

基于项目内 [merchant-api.md](merchant-api.md) 实现的独立前后端网站。技术栈为 React 19、Vite、Express 5、Node.js 24 和 SQLite。默认暖白 / 深绿界面，适配电脑与手机。原始接口文档保留不变。

## 本地运行

需要 Node.js 24+。

```bash
npm install
npm run setup
npm run dev
```

`setup` 生成本机 `.env`、独立加密密钥及随机管理员密码，密码仅在终端显示一次。已有 `.env` 时拒绝覆盖。首次初始化后请保存密码。

- 前台兑换：<http://localhost:3200/>
- 订单查询：<http://localhost:3200/orders>
- 使用帮助：<http://localhost:3200/help>
- 后台管理：<http://localhost:3200/limdh-admin>

后台登录后打开「服务配置」，填写商户 API Key，以及上游商户兑换站地址中 `/s/` 后的站点标识并保存。站点必须已启用，且必须与 API Key 属于同一商户；例如地址为 `https://admin-lm.zdhxylc.shop/s/example` 时填写 `example`。未配置时页面明确展示「待配置」。配置状态仅表示已保存，不代表密钥有效或已确认两个配置属于同一商户。

开发模式仅绑定 `127.0.0.1`。请使用配置中的 `http://localhost:3200` 访问，避免与 `APP_ORIGIN` 不一致导致来源校验失败。API Key 通过后台设置，**不要放进前端代码或 `VITE_*` 环境变量**。

Windows 上，服务启动时会自动读取已启用的系统 HTTPS 代理，并遵循上游域名的代理例外；显式设置的 `HTTPS_PROXY` 优先。系统代理设置改变后需重启服务。关闭自动检测可在 `.env` 中设置 `USE_WINDOWS_SYSTEM_PROXY=0`。Linux 和 Docker 可通过 `HTTPS_PROXY` / `NO_PROXY` 显式配置代理。自动检测不处理 PAC 自动配置脚本；这种情况下请显式配置 `HTTPS_PROXY`。TLS 证书仍会正常校验。

## 已实现能力

| 入口 | 能力 |
| --- | --- |
| 前台 | 上游验证单个 CDK，验证通过后填写 Session、账号预览、提交确认 |
| 前台批量 | 先导入卡密并逐张验证，通过后按顺序输入或导入 Session、最多 50 组、顺序提交、暂停后续提交、下载回执 |
| 订阅查询 | `/subscription` 输入完整 Session 或 accessToken，实时查询 ChatGPT 套餐、有效状态、到期时间及续费状态，不保存查询凭据 |
| 订单查询 | 单个 / 批量完整订单 UUID，最多 100 条；当前浏览器历史记录；刷新及导出 |
| 订单进度 | 前 30 秒每 3 秒查询，之后每 8 秒，3 分钟暂停；后台标签页暂停查询；`needs_attention` 停止自动查询 |
| 后台工作台 | 本站订单统计、最近 100 笔订单、未知提交数、最小化操作审计 |
| 后台订单 | 查询当前 API Key 所属商户的历史 API 订单，单个 / 批量查询 |
| 银行卡直充 | 仅管理员，单个 / 批量 JSON，支持 go、plus、pro5、pro20、pro50；支付及积分消耗确认 |
| 卡号邮箱补查 | 仅管理员，调用文档 `/third-party/orders/lookup`，保留每笔结果对应的订单号 |
| 服务配置 | API Key 加密保存 / 替换 / 删除，网站名称、公告、售后说明、维护开关、批量入口开关 |

所有上游请求都由后端发送。订单使用 `https://admin-lm.zdhxylc.shop/api/v1`，卡密预验证使用上游公开兑换站的 `/api/v2/sites/{站点标识}/preview`；两者固定在同一 HTTPS 主机，禁止重定向及任意代理地址。订单 API 遵循 HTTP 成功且 `code=0` 的双重判定。

项目内商户 API 文档未提供独立卡密预验证；这里使用上游公开兑换站当前使用的预览接口，接口契约可能随上游变化。预验证成功表示当时上游兑换站接受该卡密，不能保证最终下单成功；订单仍会由上游按 API Key 再次校验所属商户及状态。文档未提供取消订单、换码、退款、余额、套餐列表、重试订单创建或人工核验操作接口，因此没有模拟这些操作。`pro50` 原样传给接口，套餐与地区是否启用由上游决定。后台统计是本站已记录数据，不代表商户上游完整账单。

## 批量格式

第一步输入卡密，每行一张，也可以导入 TXT。全部验证通过后，第二步按相同顺序输入 Session，每行一个完整 JSON，也可以导入 TXT 或 JSON 数组；Session 必须真实、完整、有效。示例中的 `…` 只是占位符。

```text
第一张卡密
第二张卡密
```

```text
{"user":{"email":"first@example.com"},"account":{"id":"account-1"},"accessToken":"…"}
{"user":{"email":"second@example.com"},"account":{"id":"account-2"},"accessToken":"…"}
```

后台批量直充使用文档规定的完整直充请求对象数组。批量按顺序提交，间隔至少 850 ms；遇到限流、未知结果、密钥缺失等异常时停止后续提交。所有创建请求受每 IP 每小时 60 次限制，单批最多 50 条。

## 订单安全与异常恢复

- 创建订单必须携带提交标识。浏览器会话存储只记录请求 SHA-256 摘要与随机标识，不保存请求正文。后端将标识按访客身份隔离，向上游传入稳定的 `Idempotency-Key`。
- 首次创建卡密订单必须携带服务端签发的验证凭证，凭证绑定卡密、浏览器身份、商户站点且 30 分钟内有效。卡密或站点变更后需重新验证。网络中断产生的未知提交仍可使用原标识和相同内容安全重试，即使卡密此时已被上游占用。
- 相同标识及相同内容重试返回原订单；相同标识改变内容返回冲突。请求中的 JSON 对象键顺序在服务端统一处理。
- 单笔卡密网络中断且没有订单号时，可在当前浏览器选择「恢复结果未确认的原提交」，输入原卡密和先前保存的提交标识。只有匹配当前浏览器、卡密及未知状态的原提交才可继续；填写的 Session 内容必须与原提交完全一致。
- 同一卡密与进行中的同一账号会被占用。网络超时、进程中断后结果不确定时继续占用；必须以原标识和原内容恢复。未知结果不会自动按失败处理或自动释放。
- `pending_verification` 单独展示，`payment_confirmed=false` 不等于未扣款；`needs_attention` 停止自动轮询，提醒联系商家，禁止重复充值。
- 前台仅能查询当前浏览器 Cookie 身份所属订单；输入其他订单号不会向上游发起查询。换设备、清 Cookie 或浏览器身份过期后，请联系商家由后台查询，避免公开查询泄露邮箱及支付结果。
- API 不提供 CDK+邮箱补查。如果卡密提交出现未知结果且原标识丢失，需到上游商户工作台人工核实；不要直接清理本地占用记录。银行卡直充可由管理员使用完整卡号与邮箱补查。
- API Key 更换后，应确保新旧 Key 属于同一商户。不同商户的密钥不应共用这套订单数据库。

## 安全实现及边界

- API Key 和必要订单快照通过 AES-256-GCM 加密入库；API Key 从不通过配置读取接口返回。加密密钥放在环境中，与数据库分离。
- 不持久化 Session、accessToken、sessionToken、完整银行卡号、CVV 或明文 CDK。仅保存去重用 HMAC 摘要。敏感请求不得配置到反向代理、APM 或调试请求日志里。
- 管理员密码使用加盐 scrypt；HttpOnly / SameSite=Strict 身份 Cookie；生产环境 Secure 与 `__Host-` 前缀；登录旋转会话，登录权限有效 8 小时，访客身份有效 30 天。
- 服务端校验 Session 字段、JWT 的 iat/exp、卡号长度、CVV 格式、到期月份、套餐、查询数量。JWT 的本地解码仅检查结构和有效期，真正的凭据真实性及业务权限由上游预检验证。
- 所有写操作校验 CSRF token 及来源；不开放跨域；设置 CSP、禁止嵌入、禁缓存、禁 MIME 嗅探和 Referrer 泄露。生产环境不含开发模式的脚本策略例外。
- 登录最多 8 次 / 15 分钟 / IP，网站 API 最多 100 次 / 分钟 / IP，创建最多 60 次 / 小时 / IP；共享上游预算 100 次 / 分钟，低于文档 120 次上限。若同一出口 IP 有其他调用者，应在业务侧进一步降低预算。
- SQLite 使用参数化 SQL。业务审计只记录操作类型和时间，不记录请求体。数据库与 `.env` 已忽略进 Git 和 Docker 构建上下文。

这些措施降低常见风险，不能替代部署环境的访问控制、依赖维护和上线安全评估。商户后台建议额外限制管理 IP 或接入网关 MFA。当前版本使用**单 Node 进程 / 单副本**；限流在进程内，不能直接横向多副本部署。扩容前须统一会话、限流和提交锁。

订单及审计数据包含个人信息。本站最多保留 2,000 条审计记录；订单不自动删除，以免丢失处理中订单和去重保护。运营方应制定保留周期、售后处理及删除流程。请同时核实上游对凭据的保留政策。

## 重置管理员密码

先停止本地服务，在项目目录执行：

```bash
npm run admin:reset
npm run dev
```

命令生成新随机密码并在终端显示，保留数据库及加密密钥，撤销现有管理员权限。重启后新密码生效。**不要删除或随意重新生成 `ENCRYPTION_KEY`、`SESSION_SECRET`**：前者丢失将无法解密配置和订单，后者变化将破坏身份及提交幂等关联。

## 生产部署：Docker + Caddy 自动 HTTPS

1. 将代码与 `.env` 安全放置到 Linux 服务器；DNS 指向服务器，开放 80/443。
2. 首次在项目目录执行 `npm install` 和 `npm run setup`，保存管理员密码。也可在可信本地初始化，再安全传送 `.env`。
3. 修改 `.env` 中的 `APP_ORIGIN=https://您的域名`，另加一行 `SITE_DOMAIN=您的域名`。`SITE_DOMAIN` 不带协议和路径。
4. 执行以下命令。Node 端口只在内部容器网络暴露，Caddy 终止 HTTPS；`TRUST_PROXY=1` 仅适用于这个确切的一层代理拓扑。

```bash
docker compose up -d --build
docker compose logs --tail=50 app
```

应用运行在非 root 用户、只读根文件系统下，数据保存于 `app_data` 持久卷。数据库与环境密钥要分别安全备份；不要执行删除数据卷的命令。

Docker 环境重置密码：停止 app；在持有 `.env` 的宿主机运行 `npm run admin:reset` 更新哈希，然后 `docker compose up -d --force-recreate app`。会话中的管理员权限绑定密码版本，重启读取新哈希后，旧管理员权限自动失效；订单归属及幂等关联保持不变，无需修改数据卷或轮换加密密钥。

已有 Nginx 等代理时可直接运行：

```bash
npm ci
npm run build
npm start
```

生产启动要求 `APP_ORIGIN` 使用 HTTPS；建议保持 Node 仅监听本机，代理转发到 3200。确保真实 IP 头只能由可信代理设置；只有一层可信代理时才设置 `TRUST_PROXY=1`。禁止将开发服务器直接暴露到公网。

### 订阅查询接口

本站 `POST /api/subscription/query` 接收 `{ "session": "完整 Session JSON 字符串或 accessToken" }`。后端仅向固定的充值服务商地址 `https://admin-lm.zdhxylc.shop/api/v2/recharge/subscription-query` 转发 `chatgpt_token`；仅包含 accessToken 及可用的账号 ID、邮箱，不转发 sessionToken，不使用商户 API Key，不创建订单。该路径来自上游当前公开网页，未包含在项目的 v1 商户 API 文档中，若上游调整协议需要同步维护。

查询每 IP 每分钟最多 10 次，同时受全站上游预算限制。仅返回订阅字段白名单；上游缺失必需状态字段、超时或异常响应会显示查询失败，不能当作“无订阅”。上游未返回的到期、续费等字段保持未知。前端查询成功后清空 Session 输入并展示结果，查询结果不持久化。

已用浏览器检查桌面兑换页、后台登录与设置保存、订单查询，以及 390px 手机布局。界面截图见 `artifacts/frontend.jpg`、`artifacts/admin.jpg`、`artifacts/mobile.jpg`。本机没有 Docker，容器构建、Caddy 证书申请及公网部署尚未实测。

生产服务需持久化 `/app/data` 与完整环境密钥。开发数据默认在 `data/limen.sqlite`。Node 24 的 `node:sqlite` 无额外原生模块编译依赖。
